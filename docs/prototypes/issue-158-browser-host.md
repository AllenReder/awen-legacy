# #158: Tauri browser host feasibility

Status: **partial native and broker evidence, not production delivery**. A maintainer exercised the manual proof and a limited broker-connected Agent flow on macOS. Browser host delivery remains blocked until the remaining promised operations are demonstrated or explicitly ruled out. Do not infer full contract coverage from the presence of a child webview.

## Scope and existing seam

The inherited `PreviewManager` owns `(threadId, tabId)` metadata, open/navigate/resize/refresh/close/list/status events. `PreviewAutomationBroker` routes a provider's `preview_*` request to a connected desktop host. `PreviewAutomationHosts.tsx` advertises all operations only on Electron because `tauriBridge.ts` supplies no `desktopBridge.preview`. The Electron implementation obtains DOM state and input through Electron debugger and `<webview>`; those mechanisms are not available through the Tauri bridge. Preserve the manager, broker, provider tool protocol, preview IDs, profile IDs, and response/error contracts. A Tauri adapter must supply the native page and automation implementations; it must not advertise operations until they work.

The manual debug proof uses Tauri's child `WebviewBuilder` and `Webview::eval_with_callback` to act on the same page displayed in the window. It creates two simultaneously visible guests, moves/resizes/zooms and focuses one, probes persistent storage separation, and checks that a closed guest rejects another evaluation. Its button sequence does **not** connect to `PreviewAutomationBroker`; that remains a direct native check.

Both proof modes also have macOS-only **Capture** controls. Each calls [`WKWebView.takeSnapshot`](https://developer.apple.com/documentation/webkit/wkwebview/takesnapshot%28with%3Acompletionhandler%3A%29?language=objc) on the exact displayed child webview and shows the returned PNG beside the live page. In Agent mode, each button addresses the native slot bound to its Agent tab ID, so `tab_2` can be compared with the page that `preview_evaluate` controlled. This is a capability probe, not the Agent `preview_snapshot` implementation: the latter also promises structured DOM/accessibility state, diagnostics, and the image through the broker. Native compilation and capture behavior of this new probe still require a macOS run.

A second, opt-in debug mode starts the ordinary Awen window plus a native browser-proof window. `TauriProofAutomationHosts` uses the existing preview RPC subscription and response consumer to connect to `PreviewAutomationBroker`, and advertises only `status`, `open`, `navigate`, and `evaluate`. Those requests reach the displayed native guest. Other operations remain explicit capability gaps rather than being advertised without implementations. This mode is a candidate for the required Agent-contract evidence, not a production host.

## Broker round-trip check (macOS)

Keep the strict dev web server running as below. In a second terminal, start the registered dev app in Agent proof mode:

```sh
AWEN_BROWSER_HOST_PROOF=1 AWEN_BROWSER_HOST_PROOF_AGENT=1 pnpm --filter @awen/desktop build:app
```

The ordinary Awen window should show **Agent browser proof (debug)** with **Broker connected**, alongside a separate **Awen Agent browser proof** native window. Enable Agent browser access in the environment's settings. Use only `gpt-5.6-luna` or `MiniMax-M3` for a real Agent test. Ask it to call `preview_open` with the dev server's `http://localhost:<webPort>/browser-host-proof-page.html`, then `preview_status`, `preview_navigate`, and `preview_evaluate` to read and change the page's input and click count. Record each tool input/result and the visible state of the same native guest. Open a second tab with `reuseExistingTab:false` and target both returned tab IDs independently. In the debug panel, cancel a page close, then confirm it; an Agent call targeting the closed tab must return an explicit error. Any unimplemented operation should return the broker's unsupported-capability result, never a false success.

### Maintainer-reported macOS result

The maintainer ran the broker-connected mode against `http://localhost:6933/browser-host-proof-page.html` in environment `3f622771-cb8e-4213-9a41-3c6c9b869c7e`. The Agent reported successful `preview_open`/`preview_navigate` on `tab_1`; `preview_status` returned `available: true`, `visible: true`, title `Native proof page`, `loading: false`, fill viewport `430×510`. `preview_evaluate` read the live input/button/count, changed `#message` from `initial` to `agent proof`, and dispatched a synthetic click that changed `#count` from `0` to `1`. A second tab, `tab_2`, opened for an independent target check. These are reported tool results, not independently captured native UI evidence.

`preview_snapshot`, `preview_click`, and `preview_wait_for` repeatedly returned `PreviewAutomationNoAvailableHostError` in the same environment; snapshot also failed on `tab_2`. This is expected from this prototype: its registered `supportedOperations` set contains only `status`, `open`, `navigate`, and `evaluate`. The broker filters hosts by operation, so the errors do **not** show that the host, page, or tab disappeared. Restarting or opening another tab cannot add unsupported operations. Here `preview_status.available: true` means this limited native host/page is available, **not** that every `preview_*` operation is supported. `evaluate`-driven DOM changes are synthetic and do not validate trusted click/type/press input.

The maintainer then closed `tab_1` from the debug panel. A status call targeting `tab_1` failed, as closure requires, but the generic client error did not make the closed-page reason clear. Both a default `preview_open` and one with `reuseExistingTab:false` also failed. The broker retains the last tab ID as an **implicit** target until a successful new open; the debug host had treated that stale ID as an explicit request to reuse the closed tab. The host now rejects only an explicitly requested closed tab, permits an implicit stale target to create a new page, and returns the typed tab-not-found error for a closed page. On macOS, the maintainer retested the fix: `preview_status({tabId:"tab_1"})` returned `Preview tab tab_1 was not found for status.`; a default `preview_open` returned `tab_2`; `preview_status({tabId:"tab_2"})` succeeded; and `preview_open({reuseExistingTab:false})` returned a distinct `tab_3`.

In a later macOS Agent-proof run, the user reported that the debug panel's Close button released `tab_2` without showing a confirmation. The panel had used `window.confirm`, which did not provide a visible choice in that run. It now uses Awen's mounted confirmation dialog and fails closed if no dialog host is available. It ignores duplicate close requests while confirmation is pending and checks the page identity again before native close, so stale consent cannot release a replacement page. The new regression test verifies that cancellation leaves the native close command and daemon page untouched and that duplicate clicks do not queue another confirmation. After pulling commit `804ab87` onto macOS, the maintainer reported that the full close-confirmation retest passed: the dialog appeared, cancellation kept the page accessible to the Agent, confirmation closed it and produced a closed-tab result, and a subsequent open created a usable page. In the earlier user-reported run, `preview_status` and `preview_evaluate` against closed `tab_3` returned `Preview tab tab_3 was not found for status.` and `Preview tab tab_3 was not found for evaluate.` respectively. The new retest's OS version, app identity, exact tool transcript, and matching native-window capture have not been attached, so this remains maintainer-reported evidence.

This result still does not validate snapshot, trusted click/type/press/scroll, wait conditions, appearance, recording, full profile mapping, or Workbench Pane placement. Each remains a blocker for host-dependent delivery. Capture the actual tool transcript, OS version, app PID/bundle identity, and matching native-window image before treating the limited broker round trip as independently reproducible evidence.

## Reproduction

Run on **macOS 14 or later** with the registered Awen Dev app identity (`com.allenreder.awen.dev`). From this worktree, start the dev web server in one terminal, then build and launch the registered app in another:

```sh
pnpm install --frozen-lockfile
AWEN_STRICT_DEV_PORTS=1 pnpm dev:web
```

```sh
AWEN_BROWSER_HOST_PROOF=1 pnpm --filter @awen/desktop build:app
```

The registered runner bundles the proof controller at the app's local origin, selects the checkout's pinned dev web port for its test pages, and supplies that port to the proof. The feature is debug-only and does not register production preview commands. Before binding the window with Computer Use, use `cua.getState()` and `ps` to verify the running executable is the absolute `Awen Dev.app` path printed by `build:app`, its PID and data root match this worktree, the window shows the proof, and the bundle id is `com.allenreder.awen.dev`. In that window, click **Run capability sequence**. Observe both guest pages, the log's same-page message/click count, the navigated URL, rendered viewport and focus after movement/zoom, and `profile A` versus `profile B`. `profile B` must be `null`. Click **Confirm close of page A**, cancel the dialog, then click **Check page A is still open** and verify its URL is returned. Click **Confirm close of page A** again and accept the dialog; the following evaluation must report the closed tab. Reopen it and check persistent profile behavior. Capture the OS version, window/PID, log, and screen recording for the issue. Follow `AGENTS.md` Computer Use identity checks before binding any macOS window.

Before closing page A, click **Capture displayed page A** after the capability sequence. The image shown in the controller must depict page A's visible `agent typed here` input and incremented click count, at the same time those values are visible in the child page. Record the PNG dimensions and compare with the child viewport; then change the child input directly, capture again, and verify the new pixels come from that same displayed page. A blank, stale, or other-page image is a failed native capability check. This manual capture does not make Agent `preview_snapshot` available.

In Agent mode, open two tabs with the existing broker runbook, change `tab_2` using `preview_evaluate`, then click **Capture b: tab_2** in the debug panel. Compare the returned PNG with `tab_2` in the native proof window, including the changed input or click count. Capture `tab_1` separately and verify the images differ as expected. The Agent's `preview_snapshot` must still return a capability error until its full contract is implemented; do not treat the debug button as a routed Agent snapshot.

For the complete Agent-contract gate, expand and validate the native adapter for every promised `preview_*` operation against the same page visible in the Workbench. Do not run a real Agent with a model other than `gpt-5.6-luna` or `MiniMax-M3`.

## Evidence from this checkout

- Platform in this checkout: Linux. The maintainer reported both manual and limited broker-connected macOS runs, including the tool results summarized above. OS version, app identity, and native-window capture have not yet been attached.
- `pnpm typecheck` and `pnpm test`: passed. `AWEN_BROWSER_HOST_PROOF=1 pnpm --filter @awen/web build`: passed and emitted `dist/browser-host-proof.html`. `cargo fmt --check`: passed.
- `cargo check --features browser-host-proof`: blocked before checking this module because Linux development packages for `dbus-1` and WebKitGTK are absent (`libdbus-sys` cannot find `dbus-1.pc`; `webkit2gtk-4.1.pc` is also absent).
- Cross-checking the macOS capture probe from this Linux checkout stops in `objc2-exception-helper` because the host C compiler lacks the Apple `-arch` and `-mmacosx-version-min` flags. The new macOS-only Rust path has not yet passed `cargo check` or a native run on macOS.

## Host choice and delivery gate

The candidate is a Tauri child-webview host keyed by the existing preview tab identity, with a native adapter behind the current desktop preview bridge and the existing daemon/provider protocol unchanged. A native evaluation callback can return results from the displayed guest, and separate WKWebView data stores are documented on macOS 14+ ([Tauri WebviewBuilder](https://docs.rs/tauri/2.11.5/tauri/webview/struct.WebviewBuilder.html)). This is a **provisional design**, not a supported-platform decision. Supported native platforms remain unestablished. If trusted input, snapshots, recording, profile isolation, or Agent-visible close errors cannot be demonstrated on a supported target, keep subsequent browser-host delivery blocked and raise an explicit product decision; do not substitute an external browser or silently reduce the advertised operation set.
